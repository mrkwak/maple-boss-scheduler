# ADR-0007: 저장소는 Google 스프레드시트 (교체 가능 구조)

- 상태: 제안 (2026-10-08) — 사용자 요구 "요금제 문제 없고 넣고 빼기 간단한 것, 스프레드시트도 상관없음"

## 배경
- 초안(ADR-0001)은 Supabase였다.
- Supabase 무료 플랜은 활동이 없으면 약 7일 뒤 프로젝트를 일시정지하고, 대시보드에서 수동으로 복구해야 한다는 설명이 여러 2026년 자료에 있음 [출처: 서드파티 자료, Supabase 공식 문서로는 확인 못함]. 주 1회 쓰는 지인 앱은 한 주만 건너뛰어도 멈출 수 있다.
- 이용자 약 5명, 데이터는 수백 행 수준.

## 결정
- Google 스프레드시트 1개를 DB로 쓴다. 탭 = 테이블 (구성은 PLAN.md §5).
- 서버 라우트에서만 Google 서비스 계정으로 접근. 시트는 서비스 계정 이메일과 관리자에게만 공유.
- 저장 코드는 `lib/db/`의 리포지토리 인터페이스(`list`, `get`, `insert`, `update`, `remove`) 뒤에 둔다 → Supabase 등으로 바꿀 때 이 폴더만 교체.
- 서버에서 짧은 캐시(10~30초) + 저장 직후 캐시 무효화.
- 실시간은 폴링(약 30초)으로 대체.

## 근거 (확인됨)
- Google Sheets API 한도: 프로젝트당 분당 읽기 300·쓰기 300, 사용자당 분당 읽기 60·쓰기 60, 초과 시 429 [출처: https://developers.google.com/sheets/api/limits]. 5명 규모에 충분.

## 대안
- Supabase 무료 → 관계형·Realtime 장점, 비활성 일시정지 리스크. 정기 접속 배치로 피할 수는 있으나 관리 포인트 증가.
- Vercel/기타 무료 DB(Neon, Turso 등) → 이번에 무료 한도·정지 정책을 조사하지 않음 [미확인].

## 결과
- (+) 무료, 시트를 열어 직접 보고 고칠 수 있음, 백업 = 파일 복사, 컷표 같은 설정을 사용자가 직접 수정 가능
- (−) 트랜잭션·외래키 없음 → 앱 코드에서 검증, 동시 수정은 마지막 저장이 이김
- (−) 응답이 DB보다 느림 → 캐시로 보완
